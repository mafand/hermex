# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hermex — a vehicle rental (locadora de veículos) app. PNPM monorepo with two workspace apps:

- `apps/web` — Next.js 16 frontend (atomic design components, Tailwind v4, NextAuth v5)
- `apps/api` — NestJS backend (GraphQL via Apollo, Prisma ORM, Postgres)

## General rules

- **Installing Node.js libraries: always use `pnpm install`/`pnpm add` (e.g. `pnpm --filter api add <pkg>`, `-D` for dev deps) and NEVER edit `package.json` by hand** to add, remove, or bump dependencies.

## Commands

Run from the repo root (uses `pnpm --filter`, no need to `cd` into an app):

```
pnpm dev:web            # Next.js dev server
pnpm dev:api            # Nest dev server (watch mode)
pnpm build:web / build:api
pnpm lint:web / lint:api
pnpm test:api           # vitest unit tests for the API

pnpm db:up / db:down    # start/stop the postgres docker container
pnpm db:logs

pnpm prisma:generate
pnpm prisma:migrate     # prisma migrate dev
pnpm prisma:studio
```

Single test file / e2e (from `apps/api`, since there's no root shortcut):

```
pnpm --filter api exec vitest run path/to/file.spec.ts
pnpm --filter api test:e2e          # vitest.config.e2e.ts, matches **/*.e2e-spec.ts
```

API linting uses `oxlint`, not eslint. Web linting uses `eslint` (flat config via `eslint-config-next`).

## Environment / infra

- Postgres runs via `docker-compose.yaml` (service `postgres`, container `hermex-postgres`), configured from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` env vars (see `.env.example`). `pnpm db:up` before running the API against a real database.
- API reads `DATABASE_URL` (for Prisma) and `WEB_URL` (for CORS, defaults to `http://localhost:3000`) and `PORT` (defaults to `3001`).
- Node >= 22 (`.nvmrc` pins 22); package manager is pnpm 11.17.0 (see `packageManager` field — don't use npm/yarn in this repo).

## Architecture

### apps/api (NestJS)

- Single GraphQL endpoint via `@nestjs/graphql` + Apollo (`ApolloDriver`), schema is auto-generated (`autoSchemaFile: true`, code-first) — there is no `.graphql` SDL file to hand-edit; schema comes from resolver/type decorators.
- `PrismaModule` (`src/prisma/`) is `@Global()`, so `PrismaService` is injectable anywhere without re-importing the module.
- `PrismaService` extends the generated `PrismaClient` and wires it to Postgres through `@prisma/adapter-pg` using `DATABASE_URL`; it connects/disconnects via `OnModuleInit`/`OnModuleDestroy`.
- Prisma client is generated into `src/generated/prisma` (see `generator client` output path in `prisma/schema.prisma`) — it's generated code, not hand-written, and must be regenerated (`pnpm prisma:generate`) after schema changes.
- The project uses `"type": "module"` (ESM) — relative imports between source files need explicit `.js` extensions (e.g. `from './app.module.js'`), even though the source files are `.ts`.
- New feature modules (domains) must be scaffolded with the Nest CLI, never created by hand: `pnpm --filter api exec nest generate module <name>` (plus `nest generate resolver <name>` / `nest generate service <name>` as needed). The CLI generates files in `src/<name>/` and registers them in the parent module automatically. After generating, fix the relative imports to use `.js` extensions (see ESM note above).
- Tests: unit specs run with plain `vitest` (`vitest.config.ts`, matches `**/*.spec.ts`); e2e specs use a separate config (`vitest.config.e2e.ts`, matches `**/*.e2e-spec.ts`) and boot the full `AppModule` via `@nestjs/testing`, issuing real HTTP requests against `/graphql` with `supertest`.

### apps/web (Next.js)

- **This is a bleeding-edge Next.js version (16) with breaking API/convention changes vs. training data.** `apps/web/AGENTS.md` (auto-generated by `next dev`, re-appears on every dev run — don't try to remove it, commit it if it shows as changed) instructs reading `node_modules/next/dist/docs/` before writing Next.js code in this app. Do this before touching routing, middleware, or other Next-specific APIs here.
- Routing uses App Router with route groups: `(public)` (e.g. `/login`) and `(private)` (e.g. `/dashboard`) under `src/app/`. Route groups don't affect the URL path — they're purely for organizing which routes are gated.
- Auth is NextAuth v5 (`next-auth@beta`), split for edge compatibility:
  - `src/auth.config.ts` — edge-safe config only (no Node-only imports); defines `pages.signIn` and the `authorized` callback that gates `/dashboard`.
  - `src/auth.ts` — full config (`NextAuth(...)`) exporting `handlers`, `auth`, `signIn`, `signOut`; this is where credential/OAuth providers get added (currently `providers: []`, unwired — `LoginForm` renders a disabled submit button pending this).
  - `src/proxy.ts` — edge middleware entry point built from `authConfig` (note: this app uses `proxy.ts`/`export const proxy`, not the conventional `middleware.ts`/`export const config`+`default` — a Next 16 convention change; verify against the vendored docs before assuming otherwise).
  - `src/app/api/auth/[...nextauth]/route.ts` — re-exports `handlers` as `GET`/`POST`.
- Components follow atomic design under `src/components/`: `atoms/` → `molecules/` → `organisms/` → `templates/`, each with a barrel `index.ts`. Higher tiers only import from the tier(s) below (e.g. `organisms/LoginForm` composes `atoms/Button` + `molecules/FormField`). Pages under `src/app/` import from `templates`/`organisms`, not directly from `atoms`/`molecules`.
- Styling is Tailwind v4 (CSS-first config via `@tailwindcss/postcss`, no `tailwind.config.js`) — utility classes only, no CSS modules in use.
